# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Repo Is

A collection of shell scripts that scaffold new projects with opinionated defaults. Not a runnable application — the scripts generate applications.

Each script lives in its own directory alongside its detailed README; the root `README.md` is a generic hub that links to both:

- `next/new-next.sh` — scaffolds a Next.js project (App Router, TypeScript, Tailwind, shadcn/ui, Better Auth, Vercel AI SDK, Jotai; database layer chosen with `--provider`: Kysely + graphile-migrate by default, Prisma or Drizzle). Docs: `next/README.md`
- `nest/new-nest.sh` — scaffolds a NestJS project (TypeScript, Prisma, Better Auth, `@thallesp/nestjs-better-auth`). Docs: `nest/README.md`

## Tech Stack of Generated Projects

Both scripts produce projects using **pnpm**, **PostgreSQL**, and **Better Auth** with admin/apiKey/anonymous plugins. The database layer differs by script:

- **Next.js stack**: App Router (no Pages Router, no src dir), Turbopack, shadcn/ui (all components), Jotai, Vercel AI SDK, `@better-fetch/fetch`. Database, chosen with `--provider`:
  - `kysely` (default): **Kysely** (query builder, `pg` driver) with types generated by **kysely-codegen**, and **graphile-migrate** for SQL migrations. Better Auth connects via a raw `pg.Pool`.
  - `prisma`: **Prisma 7** (`prisma-client` generator, output `lib/prisma/generated`) over `@prisma/adapter-pg`, connection URL in `prisma.config.ts`. Better Auth uses its Prisma adapter.
  - `drizzle`: **drizzle-orm** over node-postgres plus **drizzle-kit**; the auth schema lives in `lib/auth-schema.ts`. Better Auth uses its Drizzle adapter.

  Better Auth's `apiKey` plugin comes from the separate `@better-auth/api-key` package rather than the `better-auth/plugins` barrel. The Better Auth code and ESLint overrides are written at scaffold time by a headless `opencode run` (see Key Patterns). The only version-pinned dependency is the Prisma toolchain at `^7`; the Node and pnpm toolchain is pinned too (see Key Patterns).
- **NestJS stack**: `@nestjs/config` (global), `@thallesp/nestjs-better-auth`, body parser disabled in `main.ts`, default port 3001. Database: **Prisma** via `@prisma/adapter-pg` with client output in `../src/prisma/generated`.

## Testing Changes to Scripts

There are no automated tests. To verify a script change:

```bash
# Next.js script: its last step runs pnpm typecheck && pnpm lint && pnpm build itself.
# A change that touches provider-specific code needs a run per affected provider.
cd next && ./new-next.sh test-app                       # kysely
cd next && ./new-next.sh --provider prisma test-app     # or drizzle

# NestJS script
cd nest && ./new-nest.sh test-app && cd test-app && pnpm prisma generate && pnpm build
```

Scripts create the project as a subdirectory of the current working directory, so
test output lands in `next/test-app` / `nest/test-app`.

Clean up test output with `rm -rf test-app`.

Note: the Next.js script does not generate the Better Auth schema at scaffold time
for any provider; the user runs `pnpm auth:generate` after `pnpm docker`. Under
kysely the Kysely types also need a live database (`kysely-codegen` reads it), so
the generated `lib/db-types.ts` ships a placeholder `DB` type that lets `pnpm build`
type-check before the first codegen. Post-setup flows (the script prints the one
for its provider; `next/README.md` lists all three):

- kysely: `pnpm docker` → `pnpm auth:generate` → the `perl` `if not exists` rewrite
  of `migrations/current.sql` → `pnpm db:watch --once` → `pnpm db:codegen` →
  `pnpm db:commit` → `pnpm dev`
- prisma: `pnpm docker` → `pnpm auth:generate` → `pnpm db:migrate` → `pnpm dev`
- drizzle: `pnpm docker` → `pnpm auth:generate` → `pnpm db:generate` →
  `pnpm db:migrate` → `pnpm dev`

Known caveat: `shadcn add --all` can pull a `react-day-picker` major (v10) that the
generated `components/ui/calendar.tsx` isn't written for, so a full `pnpm build`
type-check may fail in that component. It is unrelated to the DB/auth setup; SWC
compilation itself succeeds.

## Key Patterns in the Scripts

- Docker Compose config is generated into `docker/compose.dev.yml` (Next.js only) with Postgres, Redis, and Mailpit
- `BETTER_AUTH_SECRET` is auto-generated via `openssl rand -base64 32` with a fallback string
- **Next.js database layer (`--provider`).** `$PROVIDER` drives a `case` in each step that differs: dev deps, runtime deps, directories, `.env`, the generated DB files, `db:*` scripts, `allowBuilds`, the AI prompt and the printed next steps. Adding a provider means touching every one of those `case`s.
  - `kysely`: `lib/db.ts` (dev-global singleton) with codegen'd types in `lib/db-types.ts`; migrations run through graphile-migrate via a `.gmrc.js` that `require('dotenv/config')` (graphile-migrate does not auto-load `.env`). `DATABASE_URL`, `SHADOW_DATABASE_URL` and `ROOT_DATABASE_URL` come from env.
  - `prisma`: `prisma/schema.prisma` (datasource has no `url`), `prisma.config.ts`, `lib/prisma.ts` singleton; the script runs `prisma generate` once so the AI step can type-check against the client. `.env` uses `127.0.0.1`, not `localhost`: Prisma's engine resolves `localhost` to `::1` first and the Postgres container listens on IPv4 only. `db:migrate` passes `--name init` because `prisma migrate dev` hangs on a name prompt without a TTY.
  - `drizzle`: `lib/db.ts` (dev-global `drizzle()` over a `pg` Pool), `drizzle.config.ts`, and `lib/auth-schema.ts` as an empty module that `pnpm auth:generate` overwrites.
  - `npm pkg set` adds `typecheck`, the provider's `db:*`, `auth:generate` and `docker:*` scripts (every compose call needs `--env-file .env`, so the `docker:*` scripts carry it).
- **Script vs. AI split (Next.js).** The script runs installers and writes config that has no library API in it (`.env`, compose, package scripts, and the provider's DB files: `.gmrc.js` / `lib/db.ts` / `lib/db-types.ts`, `prisma/schema.prisma` / `prisma.config.ts` / `lib/prisma.ts`, or `drizzle.config.ts` / `lib/db.ts`). Code that breaks when a library changes its API — `auth.ts`, `lib/auth-client.ts`, `app/api/auth/[...all]/route.ts`, ESLint overrides — is written by `opencode run --auto` (model `opencode-go/deepseek-v4-pro`, override with `NNX_MODEL`) from the `ai_prompt` heredoc. The prompt states intent, not code, and tells the model to read the installed `node_modules` types. The script commits a snapshot before the AI step so its changes show in `git diff`, caps the run at `NNX_AI_TIMEOUT` seconds, and then runs `pnpm typecheck && pnpm lint && pnpm build` itself; opencode's exit code is not trusted. `OPENCODE_PERMISSION` denies all shell commands except those checks. `--no-ai` skips the step.
- **NestJS** uses Prisma with a custom output path (`../src/prisma/generated`, added to `.gitignore`) and `env("DATABASE_URL")` directly in `schema.prisma`
- **One version pin (Next.js), deliberately.** The Prisma provider pins `prisma@^7`, `@prisma/client@^7` and `@prisma/adapter-pg@^7`: the `prisma` CLI's `latest` dist-tag is an 8.0.0 RC while `@prisma/client`'s is 7.x, and a mismatched CLI and client cannot work together. The pin is removable once `npm view prisma dist-tags` and `npm view @prisma/client dist-tags` show the same major on `latest`. Nothing else is pinned. v3.0.0 removed all three pins the script used to carry, and the reasoning is worth keeping because the instinct to re-add them recurs. The `next` pin was added when `latest` briefly resolved to a preview with an unpublished SWC binary. That stopped being true, but the pin stayed — and since it downgraded Next _after_ `create-next-app` had already generated config for a newer major, it produced a broken `eslint.config.mjs` (older `eslint-config-next` is CJS with no `exports` map, so the generated flat-config import can't resolve) and silently dropped `--turbopack` from the `dev` script. The pin outlived its cause and became the defect. The `better-auth` pin was aimed at the `apiKey` plugin leaving the barrel — but the plugin was extracted into `@better-auth/api-key`, not removed, so the fix is an import change. The `kysely` pin only existed to satisfy better-auth 1.4's peer range and is moot without it.
- **Toolchain pinned to newest at scaffold time (Next.js).** `resolve_toolchain` looks up the newest Node on the `NNX_NODE` line (`lts` default, or `latest`) and the newest pnpm; `step_pin_toolchain` writes them into `package.json` `devEngines` (`runtime` + `packageManager`, both `onFail: "download"`) and `.nvmrc`. pnpm then downloads and runs on them for every later step, so only `create-next-app` uses the global install — with `--skip-install`, because pnpm 11+ rejects a pnpm-10 lockfile (default 1-day `minimumReleaseAge`). The pin step also drops create-next-app's `packageManager` field (Corepack prefers it over `devEngines`) and rewrites `pnpm-workspace.yaml` as an `allowBuilds` map, since pnpm 11+ fails on any unlisted build script (`ERR_PNPM_IGNORED_BUILDS`); the map allows the provider's build-script packages (`prisma`, `@prisma/client`, `@prisma/engines`, or `esbuild` for drizzle). The Better Auth CLI bundles every adapter and pulls `@prisma/client` and `better-sqlite3`, whose build scripts that map denies, so every `auth:generate` passes `--allow-build=@prisma/client --allow-build=better-sqlite3` whatever the provider; a new native dep in the CLI goes there too. npm refuses any command in a project whose `devEngines.runtime` doesn't match its own Node (`EBADDEVENGINES`), so `step_add_package_scripts` (the script's only `npm pkg set`) runs before the pin. pnpm 12 reads `pnpm v` as `pnpm view`: call scripts by full name.
- **The Better Auth CLI lags the runtime, and that is fine.** `@better-auth/cli`'s stable tag sits a minor version or more behind `better-auth`; verified working across that gap. Don't try to align them — there may be no corresponding CLI release. Check the _output_ instead: it needs a table for every configured plugin (`user`, `session`, `account`, `verification`, `apikey`) — a `create table` in `migrations/current.sql` (kysely), a `model` in `prisma/schema.prisma` (prisma), or a table in `lib/auth-schema.ts` (drizzle). A missing plugin table is the signal to try `@better-auth/cli@beta`.
- **Better Auth schema generation is post-setup, not in-scaffold (Next.js).** `@better-auth/cli generate` checks the live DB (the kysely `pg.Pool` adapter introspects it; under prisma the CLI checks the schema against it), so it cannot run during scaffolding (no Postgres yet). The script only adds an `auth:generate` script (`--output migrations/current.sql` for kysely, `lib/auth-schema.ts` for drizzle, the default `prisma/schema.prisma` for prisma); the user runs it after `pnpm docker`. NestJS still generates the Prisma schema at scaffold time (offline).
- **graphile-migrate / Postgres gotchas (Next.js).** `.env` sets `ROOT_DATABASE_URL` to `template1` (not `postgres`) because graphile-migrate rejects a `connectionString` equal to the root/shadow strings. The Postgres volume mounts at `/var/lib/postgresql` (not `/var/lib/postgresql/data`) for `postgres:18`'s data-dir layout.

## When Editing Scripts

- The scripts use heredocs (`cat > file <<EOL ... EOL`) to generate files. Watch for shell variable expansion — `$` characters intended for the generated code must be escaped as `\$`.
- Generated file paths differ between Next.js (root-level `lib/`, `auth.ts`) and NestJS (`src/` directory structure).
- A Next.js workaround the model can't learn from the installed types (graphile-migrate quirks, compose flags, codegen excludes) goes in the script. One that is about a library API goes in `ai_prompt` as intent, never as code.
- Think hard before adding a version pin. The Next.js script has one (Prisma `^7`), and an earlier set caused more breakage than it prevented (see Key Patterns). If `latest` genuinely breaks, verify the claim against the registry rather than reasoning from memory — `npm view <pkg> dist-tags` and `npm view <pkg>@<ver> version` settle most questions in seconds, and "is the platform binary actually published?" is checkable directly. Pin the narrowest thing that fixes it, and write down what would make the pin removable, since a pin whose reason is undocumented outlives the problem.
- Validate with `bash -n next/new-next.sh` (or `nest/new-nest.sh`), then `--dry-run` for Next.js, before running a full scaffold. There's no lighter substitute for correctness here than the real `Testing Changes to Scripts` flow above — the script has no linter/typecheck of its own.
- After modifying dependencies or fixing a scaffold bug, keep the **script's own README** (`next/README.md` or `nest/README.md`) and this file's Key Patterns section in sync — both have drifted out of date after fixes before. The root `README.md` is generic and usually doesn't need touching unless installation or repo layout changes.
- For scaffold failures (script bug vs. upstream package break, Docker/Postgres/graphile-migrate issues, generated-project build errors), use the `scaffold-debugger` subagent (`.claude/agents/scaffold-debugger.md`) rather than debugging ad hoc — it documents this repo's known failure categories.
