# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Repo Is

A collection of shell scripts that scaffold new projects with opinionated defaults. Not a runnable application — the scripts generate applications.

Each script lives in its own directory alongside its detailed README; the root `README.md` is a generic hub that links to both:

- `next/new-next.sh` — scaffolds a Next.js project (App Router, TypeScript, Tailwind, shadcn/ui, Kysely + graphile-migrate, Better Auth, Vercel AI SDK, Jotai). Docs: `next/README.md`
- `nest/new-nest.sh` — scaffolds a NestJS project (TypeScript, Prisma, Better Auth, `@thallesp/nestjs-better-auth`). Docs: `nest/README.md`

## Tech Stack of Generated Projects

Both scripts produce projects using **pnpm**, **PostgreSQL**, and **Better Auth** with admin/apiKey/anonymous plugins. The database layer differs by script:

- **Next.js stack**: App Router (no Pages Router, no src dir), Turbopack, shadcn/ui (all components), Jotai, Vercel AI SDK, `@better-fetch/fetch`. Database: **Kysely** (query builder, `pg` driver) with types generated by **kysely-codegen**, and **graphile-migrate** for SQL migrations. Better Auth connects via a raw `pg.Pool`, and its `apiKey` plugin comes from the separate `@better-auth/api-key` package rather than the `better-auth/plugins` barrel. The Better Auth code and ESLint overrides are written at scaffold time by a headless `opencode run` (see Key Patterns). Nothing is version-pinned.
- **NestJS stack**: `@nestjs/config` (global), `@thallesp/nestjs-better-auth`, body parser disabled in `main.ts`, default port 3001. Database: **Prisma** via `@prisma/adapter-pg` with client output in `../src/prisma/generated`.

## Testing Changes to Scripts

There are no automated tests. To verify a script change:

```bash
# Next.js script: its last step runs pnpm typecheck && pnpm lint && pnpm build itself
cd next && ./new-next.sh test-app

# NestJS script
cd nest && ./new-nest.sh test-app && cd test-app && pnpm prisma generate && pnpm build
```

Scripts create the project as a subdirectory of the current working directory, so
test output lands in `next/test-app` / `nest/test-app`.

Clean up test output with `rm -rf test-app`.

Note: the Next.js script cannot generate the Better Auth schema **or** the Kysely
types at scaffold time — both need a live database (the Better Auth `pg` adapter
introspects the DB; `kysely-codegen` reads it). The generated `lib/db-types.ts`
ships a placeholder `DB` type so `pnpm build` type-checks before the first codegen.
Full post-setup flow: `pnpm docker` → `pnpm auth:generate` → the `perl` `if not exists`
rewrite of `migrations/current.sql` → `pnpm db:watch --once` → `pnpm db:codegen` →
`pnpm db:commit` → `pnpm dev`.

Known caveat: `shadcn add --all` can pull a `react-day-picker` major (v10) that the
generated `components/ui/calendar.tsx` isn't written for, so a full `pnpm build`
type-check may fail in that component. It is unrelated to the DB/auth setup; SWC
compilation itself succeeds.

## Key Patterns in the Scripts

- Docker Compose config is generated into `docker/compose.dev.yml` (Next.js only) with Postgres, Redis, and Mailpit
- `BETTER_AUTH_SECRET` is auto-generated via `openssl rand -base64 32` with a fallback string
- **Next.js** uses Kysely (`lib/db.ts`, a dev-global singleton) with codegen'd types in `lib/db-types.ts`; migrations are managed by graphile-migrate via a `.gmrc.js` that `require('dotenv/config')` (graphile-migrate does not auto-load `.env`). DB connection strings (`DATABASE_URL`, `SHADOW_DATABASE_URL`, `ROOT_DATABASE_URL`) come from env. `npm pkg set` adds `typecheck`, `db:*`, `auth:generate` and `docker:*` scripts (every compose call needs `--env-file .env`, so the `docker:*` scripts carry it).
- **Script vs. AI split (Next.js).** The script runs installers and writes config that has no library API in it (`.env`, compose, `.gmrc.js`, `lib/db.ts`, `lib/db-types.ts`, package scripts). Code that breaks when a library changes its API — `auth.ts`, `lib/auth-client.ts`, `app/api/auth/[...all]/route.ts`, ESLint overrides — is written by `opencode run --auto` (model `opencode-go/deepseek-v4-pro`, override with `NNX_MODEL`) from the `ai_prompt` heredoc. The prompt states intent, not code, and tells the model to read the installed `node_modules` types. The script commits a snapshot before the AI step so its changes show in `git diff`, caps the run at `NNX_AI_TIMEOUT` seconds, and then runs `pnpm typecheck && pnpm lint && pnpm build` itself; opencode's exit code is not trusted. `OPENCODE_PERMISSION` denies all shell commands except those checks. `--no-ai` skips the step.
- **NestJS** uses Prisma with a custom output path (`../src/prisma/generated`, added to `.gitignore`) and `env("DATABASE_URL")` directly in `schema.prisma`
- **No version pins (Next.js), deliberately.** v3.0.0 removed all three pins the script used to carry, and the reasoning is worth keeping because the instinct to re-add them recurs. The `next` pin was added when `latest` briefly resolved to a preview with an unpublished SWC binary. That stopped being true, but the pin stayed — and since it downgraded Next _after_ `create-next-app` had already generated config for a newer major, it produced a broken `eslint.config.mjs` (older `eslint-config-next` is CJS with no `exports` map, so the generated flat-config import can't resolve) and silently dropped `--turbopack` from the `dev` script. The pin outlived its cause and became the defect. The `better-auth` pin was aimed at the `apiKey` plugin leaving the barrel — but the plugin was extracted into `@better-auth/api-key`, not removed, so the fix is an import change. The `kysely` pin only existed to satisfy better-auth 1.4's peer range and is moot without it.
- **The Better Auth CLI lags the runtime, and that is fine.** `@better-auth/cli`'s stable tag sits a minor version or more behind `better-auth`; verified working across that gap. Don't try to align them — there may be no corresponding CLI release. Check the _output_ instead: `migrations/current.sql` needs a `create table` for every configured plugin (`user`, `session`, `account`, `verification`, `apikey`). A missing plugin table is the signal to try `@better-auth/cli@beta`.
- **Better Auth schema generation is post-setup, not in-scaffold (Next.js).** With the `pg.Pool` adapter, `@better-auth/cli generate` introspects the live DB, so it cannot run during scaffolding (no Postgres yet). The script only adds an `auth:generate` script (`@better-auth/cli@latest generate --yes --output migrations/current.sql`); the user runs it after `docker compose up`. NestJS still generates the Prisma schema at scaffold time (offline).
- **graphile-migrate / Postgres gotchas (Next.js).** `.env` sets `ROOT_DATABASE_URL` to `template1` (not `postgres`) because graphile-migrate rejects a `connectionString` equal to the root/shadow strings. The Postgres volume mounts at `/var/lib/postgresql` (not `/var/lib/postgresql/data`) for `postgres:18`'s data-dir layout.

## When Editing Scripts

- The scripts use heredocs (`cat > file <<EOL ... EOL`) to generate files. Watch for shell variable expansion — `$` characters intended for the generated code must be escaped as `\$`.
- Generated file paths differ between Next.js (root-level `lib/`, `auth.ts`) and NestJS (`src/` directory structure).
- A Next.js workaround the model can't learn from the installed types (graphile-migrate quirks, compose flags, codegen excludes) goes in the script. One that is about a library API goes in `ai_prompt` as intent, never as code.
- `agents/new-next/` is the agent-skill version of the Next.js scaffold, kept as a reference; its `references/troubleshooting.md` lists the failures seen in real runs.
- Think hard before adding a version pin. The Next.js script has none left, and the last set caused more breakage than it prevented (see Key Patterns). If `latest` genuinely breaks, verify the claim against the registry rather than reasoning from memory — `npm view <pkg> dist-tags` and `npm view <pkg>@<ver> version` settle most questions in seconds, and "is the platform binary actually published?" is checkable directly. Pin the narrowest thing that fixes it, and write down what would make the pin removable, since a pin whose reason is undocumented outlives the problem.
- Validate with `bash -n next/new-next.sh` (or `nest/new-nest.sh`), then `--dry-run` for Next.js, before running a full scaffold. There's no lighter substitute for correctness here than the real `Testing Changes to Scripts` flow above — the script has no linter/typecheck of its own.
- After modifying dependencies or fixing a scaffold bug, keep the **script's own README** (`next/README.md` or `nest/README.md`) and this file's Key Patterns section in sync — both have drifted out of date after fixes before. The root `README.md` is generic and usually doesn't need touching unless installation or repo layout changes.
- For scaffold failures (script bug vs. upstream package break, Docker/Postgres/graphile-migrate issues, generated-project build errors), use the `scaffold-debugger` subagent (`.claude/agents/scaffold-debugger.md`) rather than debugging ad hoc — it documents this repo's known failure categories.
